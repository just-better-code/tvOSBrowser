## Purpose and acceptance

A magnet or `.torrent` link opened from a website should immediately show the built-in torrent library, select the imported torrent, allow file selection, and play supported media in the app while verified pieces arrive. The same visible result should hold for an ordinary link, `target="_blank"`, and a main-frame response that identifies a torrent by MIME type or attachment filename. Duplicate imports should open the existing torrent. The page should remain available when import fails. Observe interaction on the bedroom Apple TV with the user's permission; do not use the simulator during this work.

## Engine version decision

User decision on 2026-10-04: stay on the linked libtorrent 1.2.17 unless a concrete required capability or problem makes migration necessary. Do not upgrade merely because 2.1 is newer. The needed file priorities and time-critical piece APIs are already present in its bundled headers. Version 2.0 adds BitTorrent v2 and hybrid torrents; 2.1 adds WebTorrent peers. Those capabilities are not prerequisites for the initial v1 magnet and `.torrent` flow. See the official [2.0](https://www.libtorrent.org/upgrade_to_2.0-ref.html) and [2.1](https://www.libtorrent.org/upgrade_to_2.1-ref.html) migration guides.

A 2.1 migration is technically feasible but out of scope under this decision: the current [Apple XCFramework source](https://github.com/danylokos/libtorrent-Apple/releases) offers only 1.2.17, so a 2.1 tvOS device/simulator framework would need to be built or sourced and verified; the project would need at least C++17. The current manager uses a single SHA-1 hash as its identifier (`BrowserTorrentManager.mm:33`, `:121`, `:154`, `:193`), whereas v2/hybrid torrents need `info_hash_t` and potentially both v1 and v2 hashes. Torrent loading and resume-data handling also change. Keep the torrent identity and engine boundary explicit during initial implementation. Reconsider migration only for a demonstrated requirement such as v2-only torrents, WebTorrent peers, or a fix unavailable on 1.2.

## Current prototype and gaps

- `BrowserTorrentManager.mm` imports magnets and torrent data, tracks torrents and files, persists skipped file indices, and gives selected media high file and piece priority. A magnet starts sequential downloading before metadata and file selection. Manager access and `sources.plist` updates are not fully serialized.
- `BrowserTorrentLibraryViewController.m` can display torrents/files, skip files, and select supported media. `importTorrentRequest:` downloads a temporary file and rejects one over 16 MB before reading it; it does not explicitly transfer cookies from `WKHTTPCookieStore` or resolve response-to-original-request identity.
- `BrowserTorrentAssetLoader.m` polls every 250 ms, asks the manager for every file while processing a request, then reads only verified pieces. Its path-to-file-index conversion is permissive. Playback and seeking have not been observed working in the simulator with the latest file-selection changes.
- `ViewController.m` intercepts ordinary magnet and `.torrent` URL navigation but only adds the torrent and tells the user to open the menu. New-tab and page-action paths do not share that interception. `BrowserWebView.m` lacks a main-frame navigation-response policy for MIME/attachment detection.
- The saved HTML examples page is for libtorrent 2.1.0; do not copy 2.1 API usage into the linked 1.2.17 build.

## Milestones

1. **Open immediately from known links.** Add a shared request classifier/handler. Present the library immediately, select existing or newly imported magnets, and show fetching/import errors in the library for `.torrent` URLs. Route ordinary navigation, WebKit new windows, and the page-action coordinator through it. Keep non-torrent navigation unchanged.
2. **Recognize response-defined torrents.** Add a main-frame response-policy route for `application/x-bittorrent` and attachment filenames ending in `.torrent`. Associate the response with its original request across redirects; preserve method/body and website cookies where possible. Bound the download before and after transfer, avoid duplicate imports, and leave unsupported authenticated/form cases with an explicit error rather than retrying an unrelated GET. Do not intercept subresources or HTML.
3. **Make selection and playback consistent.** Decide when to leave metadata-only mode, serialize manager state, persist selection/resume data, and reapply active playback piece priorities after file-priority changes. Validate file indices, handle pause/remove during loading, and make resource polling proportional to the selected file rather than the whole torrent.
4. **Observe the user flow.** The user authorized the bedroom Apple TV on 2026-10-04 and requested no simulator use for now. Build/install there when ready and use a lawful known magnet plus a `.torrent` URL to observe import, duplicate selection, file skip/resume, early playback/seek, restart, remove, and network failure.
5. **Then consider link discovery UI.** Add the proposed top-right link picker only after the direct click flow works.
